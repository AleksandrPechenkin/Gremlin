1. Для каждого листа Владимир и месяца горизонта воспроизведена логика `procurement_planning.gs`: якорь 01.MM, сумма «Заказали, шт» по nmId, колонки «Артикул ВБ» и «Заказали, шт» (в т.ч. не левее якоря). 2. **«Новый» якорь** — даты 01.MM в строке **> 4** отбрасываются при выборе, если есть кандидаты выше.
3. **«Старый» якорь** — все даты месяца участвуют в максимуме суммы.
4. Строки **03**: для Gremlin — только источник Gremlin; для Tesfe — только Tesfe/Общий без Gremlin и без Ozon.
5. Округление для сравнения с 03: `ceil(сырой / 24) * 24` (упрощение; в скрипте — коробка из справочника).

## Выявленные проблемы (до правки кода)
- На листе Gremlin для одного и того же месяца встречается **несколько** ячеек с датой 1-го числа в **разных колонках** и иногда в **разных строках** шапки.
- Алгоритм «максимум суммы по nmId» выбирал **нижний** (например, строка 5) дубль месяца с **другой** колонкой «Заказали, шт», из-за чего по многим артикулам подставлялись завышенные числа; после округления до коробки расхождение с визуально «правильным» блоком усиливалось.
- На листе **Общий (Tesfe)** даты месяца часто **далеко справа**, а «Артикул ВБ» — **слева**; без поиска ВБ слева от якоря план с листа **не читался** (в xlsx ранее `WB_col=-1`). В `procurement_planning.gs` добавлен такой fallback и расширена полоса «Заказали, шт» до `max(wb+45, anchor+45)`.

## Ограничения сверки
- Сравнение с **03** через фиксированные **24 шт/кор** — упрощение; в `procurement_planning.gs` коробка из справочника, часть расхождений — **только из-за коробки**.
- Выгрузка **xlsx** может отличаться от текущих Google Таблиц.
- Строки **Gremlin+Tesfe** в отчёте не сверяются как сумма двух листов (нужна отдельная логика).

Полный список отличий — в CSV (колонка **sheet**): `reports\plan_reconciliation_diffs.csv`.
