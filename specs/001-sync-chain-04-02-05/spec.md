# Feature Specification: Цепочка отгрузки 04→02→05 одним действием

**Feature Branch**: `001-sync-chain-04`

**Created**: 2026-05-19

**Status**: Draft

**Input**: User description: «Автоматизация цепочки 04→02→05 одним пунктом меню в книге 04: Сводная 01→02 + пересчёт транзита в 02 + safe-наполнение Партий_в_рейсе в 05. Сейчас это 3 ручных клика по разным книгам.»

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Один запуск после отгрузки в рейс (Priority: P1)

Как оператор снабжения/логистики, после того как в заказной сводке (книга 01) для
отгружаемых позиций проставлены статус «в пути в Москву» и идентификатор рейса, я хочу
**одним действием из книги-хаба (04)** обновить транзитный склад и подтянуть новые
партии в расчёт себестоимости, чтобы не переключаться между тремя таблицами и меню.

**Why this priority**: устраняет основную операционную боль — ручную цепочку из трёх
шагов, типичную при каждой отгрузке.

**Independent Test**: после подготовки тестовых строк в «Сводной» с заполненным рейсом
выполнить новое действие из книги 04; убедиться, что «Сводная» в книге 02 актуальна,
движения транзита пересчитаны, в «Партии_в_рейсе» появились только новые пары
рейс+артикул без изменения уже существующих строк.

**Acceptance Scenarios**:

1. **Given** в книге 01 в «Сводной» есть строки с рейсом `TR-2026-XXXX` и статусом
   отгрузки, **When** оператор запускает боевую цепочку из книги 04, **Then** лист
   «Сводная» в книге 02 соответствует источнику в 01, транзитные движения и остатки
   пересчитаны, в книге 05 в «Партии_в_рейсе» добавлены только отсутствующие строки
   для этого рейса.
2. **Given** в «Партии_в_рейсе» уже есть строка для `(рейс, артикул)` с вручную
   заполненными полями, **When** оператор запускает боевую цепочку, **Then** эта
   строка не изменяется (режим безопасного добавления).
3. **Given** оператор хочет проверить последствия без записи, **When** запускает
   пробный прогон (dry-run), **Then** он видит сводку по каждому шагу (что было бы
   скопировано/добавлено/пересчитано) без изменения данных в 02 и 05.

---

### User Story 2 — Понятный отчёт об ошибке (Priority: P2)

Как оператор, если один из шагов цепочки не удался (нет доступа к книге, пустая
сводка, ошибка пересчёта), я хочу увидеть **на каком шаге остановилось** выполнение и
что уже успело выполниться, чтобы не гадать, нужно ли повторять всё с начала.

**Why this priority**: снижает риск «полусинхронизированного» состояния при сбоях.

**Independent Test**: симулировать сбой (например, неверный id книги 02 в настройках);
запустить цепочку; проверить сообщение и запись в журнале синхронизации.

**Acceptance Scenarios**:

1. **Given** шаг копирования «Сводной» в 02 завершился успешно, **When** шаг
   пересчёта транзита завершился ошибкой, **Then** оператор видит явное указание шага 2,
   а шаг 3 не выполняется.
2. **Given** любой исход цепочки, **When** выполнение завершено (успех или ошибка),
   **Then** в журнале хаба (книга 04) есть запись с меткой операции цепочки и итогом.

---

### User Story 3 — Сохранение привычных отдельных действий (Priority: P3)

Как опытный пользователь, я хочу по-прежнему иметь возможность запускать каждый шаг
**по отдельности** через существующие пункты меню в соответствующих книгах, чтобы
отлаживать или выполнять только часть процесса.

**Why this priority**: не ломать отлаженные сценарии и обучение новых сотрудников.

**Independent Test**: убедиться, что старые пункты меню (снимок 01→02, пересчёт
транзита в 02, safe-партии в 05) остаются доступны и работают как до фичи.

**Acceptance Scenarios**:

1. **Given** развёрнута новая цепочка, **When** оператор открывает меню синхронизации
   в 04 и меню транзита/себестоимости в 02/05, **Then** прежние одиночные пункты
   присутствуют и не удалены.

### Edge Cases

- Книга 03 не участвует в цепочке: копирование «Сводной» только в 02 (не в 03).
- В 01 нет листа «Сводной» или он пуст — цепочка останавливается с понятной ошибкой
  на шаге 1, шаги 2–3 не выполняются.
- Не заданы Script Properties для id книг 01/02/05 — ошибка настройки до записи данных.
- Два оператора одновременно запускают цепочку — поведение не хуже, чем у текущих
  потоков синхронизации (блокировка/очередь как у существующего снимка 01→02).
- В «Сводной» нет новых пар рейс+артикул для 05 — шаг 3 завершается успешно с нулём
  добавлений; шаги 1–2 при этом всё равно выполняются, если не прерваны ошибкой.
- Долгое выполнение (много строк) — оператор получает итоговое сообщение или ошибку
  таймаута с указанием шага; частичный прогресс отражён в журнале.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставить в книге 04 (хаб) **один пункт меню** для
  запуска полной цепочки отгрузки (боевой режим с подтверждением).
- **FR-002**: Система MUST предоставить **пробный прогон (dry-run)** той же цепочки
  без записи в книги 02 и 05 (допускается чтение и отчёт).
- **FR-003**: Шаг 1 цепочки MUST скопировать актуальную «Сводную» из книги 01 в книгу
  02 с тем же смыслом, что существующий операционный снимок 01→02 (без шага 01→03).
- **FR-004**: Шаг 2 MUST пересчитать движения и остатки транзитного склада в книге
  02 на основе «Сводной» в этой книге (эквивалент «Пересчитать движения и остатки»).
- **FR-005**: Шаг 3 MUST выполнить **безопасное** наполнение «Партии_в_рейсе» в книге
  05 из «Сводной» книги 01: только новые `(рейс, артикул)`, без изменения существующих
  строк; перед боевым шагом 3 MUST создаваться снимок «Партии_в_рейсе», как в текущем
  одиночном safe-процессе.
- **FR-006**: При ошибке на шаге N шаги N+1 MUST NOT выполняться; оператору MUST
  быть показано номер/название шага и текст ошибки.
- **FR-007**: Каждый запуск цепочки MUST записывать итог в журнал синхронизации хаба
  (успех, dry-run, ошибка с шагом).
- **FR-008**: Существующие отдельные пункты меню для шагов 1–3 MUST остаться
  доступными (обратная совместимость).
- **FR-009**: Боевая цепочка MUST запрашивать подтверждение с кратким описанием трёх
  шагов до начала записи.

### Key Entities

- **Сводная (01)**: операционный источник позиций, статусов, рейса, количеств.
- **Сводная (02)**: копия для транзитного учёта; вход для пересчёта движений.
- **Партии_в_рейсе (05)**: производный лист партий по рейсам для себестоимости;
  ключ `(SHIPMENT_ID, Артикул ВБ)`.
- **Рейс (`SHIPMENT_ID`)**: идентификатор отгрузки, формат `TR-YYYY-NNNN`.
- **Журнал синхронизации (04)**: аудит операций хаба.
- **Книга-хаб (04)**: точка запуска цепочки и настройки id книг 01–05.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Оператор выполняет полный цикл «отгрузка в рейс → отражение в транзите
  и партиях» **не более чем за 2 действия** в UI (подтверждение + один запуск) вместо
  переключения между тремя книгами.
- **SC-002**: В **95%** успешных прогонов на тестовом наборе (≥10 строк с рейсом)
  результат совпадает с последовательным ручным запуском трёх отдельных операций
  (сверка количества строк и ключевых полей в 02 и 05).
- **SC-003**: При сбое на шаге 2 или 3 оператор определяет проблемный шаг **менее
  чем за 1 минуту** по сообщению UI или записи журнала (без чтения кода).
- **SC-004**: За первый месяц после внедрения число обращений «забыли пересчитать
  транзит / партии после снимка» снижается (качественно: владелец подтверждает
  отсутствие типичных пропусков шага 2 или 3).

## Assumptions

- Целевые пользователи — сотрудники, уже использующие меню «Синхронизация книг» в 04
  и знакомые с ручной цепочкой из `PROJECT_CONTEXT.md`.
- Копирование 01→03 **вне scope** этой фичи (остаётся отдельным пунктом меню).
- Режим наполнения партий — только **safe**; `refresh_qty` и `full_rebuild` — только
  через существующие пункты в книге 05.
- Script Properties для id книг 01, 02, 04, 05 уже настроены (как для текущей
  синхронизации).
- Сбор «Сводной» в 01 выполняется отдельно (расписание или вручную) до запуска цепочки.
- Лимит времени GAS учитывается на этапе плана; при очень больших объёмах возможен
  отдельный follow-up (разбиение или фоновые триггеры) — не в v1, если не укладывается
  в типичный объём отгрузки.
